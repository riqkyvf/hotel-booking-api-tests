# Автотесты Hotel Booking API

Этот репозиторий содержит интеграционные тесты отдельного приложения `hotel-booking-api`. Используй Python 3.14.2 из [CI](.github/workflows/api-tests.yml) и зависимости из [requirements.txt](requirements.txt).

## Где вносить изменения

- `tests/` — сценарии по областям API. Проверки на стыке областей размещай рядом с тестами основного правила.
- [tests/conftest.py](tests/conftest.py) — общие фикстуры. Фикстуры одного модуля держи рядом с его тестами. Используй собственные тестовые сущности и параметризуй однотипные варианты.
- `api/` — HTTP-запросы на requests. Проверки результата оставляй в сценариях. Для общего контракта ошибок переиспользуй [assert_api_error](tests/assertions.py). Параметры находятся в `data/`, JSON Schema ответов — в `schemas/`.
- [db.py](db.py) — подготовка дат конкретных тестовых броней и чтение состояния и истории. Статусы меняет приложение. После успеха проверяй сохранённое состояние, после отказа — отсутствие нежелательных изменений.

## Запуск и диагностика

- Используй выделенный тестовый стенд. Тесты изменяют данные, которые остаются в локальной базе. Порядок подготовки и условия запуска описаны в [инструкции](docs/running.md#подготовка-стенда). Перед прогоном проверь `/api/v1/health/ready`.
- Настройки бери из [.env.example](.env.example) и [описания стенда](docs/running.md#подготовка-стенда). Храни `.env` локально. Для `db` указывай ту же PostgreSQL, что использует API. Для проверки истечения JWT используй ключ подписи этого тестового API.
- Запускай pytest из корня автотестов. Полный локальный прогон состоит из [двух фаз](docs/running.md#наборы-и-полный-прогон). Подготовка `isolated_admin` меняет роли, поэтому локально запускай её на временном стенде через [скрипт](scripts/run_last_admin_tests.py). Флаг `--reuse-ci-stand` предназначен только для финальной фазы `full` в CI. [Условия запуска](docs/running.md#последний-активный-администратор)
- В [CI](.github/workflows/api-tests.yml) на PR и push в `main` запускается `smoke`. Вручную доступны `smoke` и `full`. Для диагностики сверяй Allure, JUnit и журналы контейнеров. [Отчёты](docs/running.md#allure-и-результаты-ci)

## Контракт и память проекта

- Сверяй ожидаемое поведение с [требованиями и REST-спецификацией](docs/product-risks.md#контракт-и-модель-продукта) версии API из workflow. Уточнения из других версий отмечай отдельно и указывай источник.
- В начале задачи читай [банк памяти](docs/memory-bank.md) для контекста. Существенные сведения проверяй по первоисточникам. При расхождении укажи его и обозначь неопределённость.
- Актуализируй память, когда меняется решение, подтверждённый факт или существенный открытый вопрос. Обновляй существующую запись по теме, указывай источник и условия применимости, убирай устаревшие сведения. Храни полезный для работы контекст, исключая переписку, секреты, персональные данные, сырые логи и промежуточные отчёты.
