# Автотесты Hotel Booking API

[![API tests](https://github.com/riqkyvf/hotel-booking-api-tests/actions/workflows/api-tests.yml/badge.svg?branch=main)](https://github.com/riqkyvf/hotel-booking-api-tests/actions/workflows/api-tests.yml)

Интеграционные тесты [Hotel Booking API](https://github.com/riqkyvf/hotel-booking-api) на **Python, pytest и requests**. Набор охватывает 29 API-операций: авторизацию, каталог отелей и номеров, доступность, бронирования, тестовые платежи, администрирование и health.

[Риски и обоснование проверок](docs/product-risks.md) · [Запуск и отчёты](docs/running.md) · [Результаты CI](https://github.com/riqkyvf/hotel-booking-api-tests/actions/workflows/api-tests.yml)

## Ключевые риски и автотесты

| Что может пойти не так | Как тесты это замечают | Где запускаются |
| --- | --- | --- |
| **R-02.** Два гостя бронируют один номер на пересекающиеся даты | Если бронь уже существует, второй запрос получает `409 ROOM_NOT_AVAILABLE`, а исходная бронь сохраняется. При параллельной отправке один запрос получает `201`, второй — `409`, и сохраняется одна бронь. [Пересечение дат](tests/bookings/test_booking_overlap.py#L59) · [Гонка бронирований](tests/bookings/test_booking_concurrency.py#L14) | `smoke` — последовательная попытка на те же даты. `full` — все варианты пересечения и гонка. |
| **R-03.** После отмены оплаченной брони нет возврата или номер остаётся занятым | Платёж переходит в `refunded`, а другой гость может забронировать те же даты. [Тест отмены и освобождения дат](tests/bookings/test_booking_cancellation.py#L66) | `smoke` и `full` |
| **R-05.** Повтор запроса создаёт вторую бронь | Тот же ключ и те же данные возвращают исходную бронь. В списке остаётся одна запись. [Тест повтора с `Idempotency-Key`](tests/bookings/test_booking_idempotency.py#L31) | `full` |
| **R-01.** Пользователь отменяет чужую бронь | API возвращает `404 NOT_FOUND`. Исходные бронь и платёж не меняются. [Тест доступа к чужой брони](tests/bookings/test_booking_access.py#L32) | `full` |

Приоритет риска определяется последствиями для гостя, отеля и данных. Для PR и push в `main` запускается `smoke`, который проверяет основной путь от поиска номера до оплаты и отмены, а также базовые отказы. `full` включает `smoke` и добавляет проверки ролей, границ, переходов состояний, повторов и конкуренции. [Обоснование приоритетов](docs/product-risks.md#риски-и-выбранные-проверки) · [Состав и запуск наборов](docs/running.md#наборы-и-полный-прогон)

## Что показывает проект

- Параметризацию границ, входных данных, ролей и состояний; собственные тестовые сущности вместо зависимости от seed.
- Проверку сохранённого состояния после успеха и отсутствия нежелательных изменений после отказа.
- Конкурентные HTTP-запросы и чтение PostgreSQL: количество записей и история позволяют заметить повторную обработку.
- CI с одноразовым API/БД, Allure, JUnit и логами Compose.

HTTP-функции находятся в `api/`, проверки результата — в сценариях. SQL готовит даты и читает состояние; переходы выполняет приложение. В [карте рисков](docs/product-risks.md) указано, что именно проверяется и какие ограничения остаются.

## Быстрый старт

Нужны Git, Python 3.14.2 и Docker Desktop в режиме Linux containers. Сначала [подготовьте отдельный API и дождитесь readiness](docs/running.md#подготовка-стенда).

В PowerShell из корня свежего клона автотестов:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Если `.env` уже есть, пропустите копирование. При необходимости [настройте переменные стенда](docs/running.md#подготовка-стенда) и запустите smoke:

```powershell
.\.venv\Scripts\python.exe -m pytest -m smoke -q
```

Полный локальный прогон выполняется в две фазы, включая отдельный временный стенд для последнего admin. [Команды и условия запуска](docs/running.md#наборы-и-полный-прогон).

Локально данные остаются в БД; общей очистки нет. CI использует одноразовый стенд и удаляет его данные после работы.

## Результаты

В [GitHub Actions](.github/workflows/api-tests.yml) можно вручную запустить `smoke` или `full`. Версия API закреплена в workflow. На странице запуска **Summary** содержит исходы фаз, версии и ссылку на артефакт с Allure HTML, JUnit и логами Compose.

## Структура

| Путь | Назначение |
| --- | --- |
| `tests/` | Сценарии по областям, общие фикстуры и контракт ошибок |
| `api/` | HTTP-функции на requests |
| `data/`, `schemas/` | Параметры и JSON Schema ответов |
| `db.py` | Подготовка дат и чтение состояния/истории |
| `scripts/` | Изолированный запуск последнего admin и сводка CI |
| `docs/` | Риски, обоснование проверок и воспроизведение запуска |
