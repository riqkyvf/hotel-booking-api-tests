# Автотесты Hotel API

Учебный проект тестирования API на Python с pytest и requests.

## Структура

```text
docs/                       Требования и тестовая документация
data/                       Статические наборы тестовых данных
    auth.py                 Наборы email и паролей для параметризации
    profile.py              Наборы изменений профиля и невалидных запросов
schemas/                    JSON Schema ответов API
api/                        Функции отправки API-запросов
tests/
    conftest.py             Настройки, генерация данных и подготовка пользователей
    test_registration.py    Проверки операции регистрации
    test_login.py           Проверки операции входа
    test_auth_flow.py       Регистрация, вход и получение профиля
    test_profile.py         Изменение профиля, валидация и сохранность данных
pytest.ini                  Настройки pytest
requirements.txt            Зависимости
.gitignore                  Исключения для Git
.env.example                Пример локальных настроек без реальных секретов
```

## Подготовка

Команды для PowerShell из корня этого проекта:

Проверенное окружение: Python 3.14.2. При создании нового окружения используйте Python 3.14; другие версии пока не проверены.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Активация окружения не требуется: команды используют Python из `.venv` напрямую.

Приложение [Hotel Booking API](https://github.com/riqkyvf/hotel-booking-api) запускается отдельно. В этом репозитории нет приложения и Compose-файла. Инструкция запуска стенда: [docs/README.md](docs/README.md). По умолчанию тесты обращаются к `http://localhost:8000/api/v1`.

### Настройки окружения

`.env` хранит локальные настройки и исключён из Git. `.env.example` хранится в Git: в нём только демонстрационные значения локального seed. Для другого стенда укажите свои значения в `.env`.

| Переменная | Назначение | Если не задана |
|---|---|---|
| `API_BASE_URL` | Адрес API с префиксом `/api/v1` | `http://localhost:8000/api/v1` |
| `API_ADMIN_EMAIL` | Email активного администратора | Ошибка подготовки только административных сценариев |
| `API_ADMIN_PASSWORD` | Пароль администратора | Ошибка подготовки только административных сценариев |

`tests/conftest.py` загружает только `.env` из корня репозитория через `python-dotenv`. Уже заданные переменные окружения имеют приоритет. Пароль не обрезается и не нормализуется. Существующий `.env` не нужно повторно копировать при обновлении проекта.

Для деактивации и реактивации нужна активная административная учётная запись. Каждый сценарий создаёт собственного пользователя и меняет его через административный API; готовая учётная запись `disabled@example.com` не используется. Состояние и права администратора остаются внешним предусловием.

## Запуск

```powershell
.\.venv\Scripts\python.exe -m pytest -v
```

Используйте Python из `.venv`, чтобы запускать тесты с зависимостями этого проекта.

### Запуск в CI

Файл `.env` в CI не нужен: задайте `API_BASE_URL` переменной окружения, а `API_ADMIN_EMAIL` и `API_ADMIN_PASSWORD` — настройками/секретами CI. Для локальной проверки другого адреса в PowerShell:

```powershell
$env:API_BASE_URL = "http://localhost:8000/api/v1"
.\.venv\Scripts\python.exe -m pytest -v --junitxml=junit.xml
```

Перед прогоном поднимите отдельный стенд и дождитесь HTTP 200 от `/api/v1/health/ready`. JUnit XML можно сохранить как артефакт CI; сам файл исключён из Git. Workflow пока не добавлен. Для воспроизводимости результата записывайте версию Python, commit тестов и commit/образ приложения. Предыдущий результат в чек-листе без версии приложения не определяет совместимость с любой его версией.

## Как поддерживать тесты

- `tests/` описывает сценарии и ожидаемые результаты; проверки остаются внутри тестов.
- `api/auth.py` и `api/users.py` отправляют запросы и возвращают Response. Функции не проверяют ожидаемый статус и не выполняют повторные попытки автоматически. `update_profile` поддерживает JSON и `raw_body`; значение токена `None` позволяет проверить отсутствие Authorization.
- При несовпадении HTTP-статуса обычный assert выводит тело ответа: `assert response.status_code == 201, response.text`.
- `schemas/` описывает общую структуру ответов. Конкретные статусы, коды и значения проверяются в тестах.
- `data/auth.py` хранит общие статические наборы email и паролей с понятными ID вариантов. Тесты импортируют их и передают в `pytest.mark.parametrize`; отдельные фикстуры для возврата этих строк не нужны. Небольшие локальные параметры, например границы длины, остаются рядом с соответствующим тестом.
- `user_data` и `login_data` только готовят данные. `registered_user` создаёт пользователя и возвращает `{"payload": user_data.copy(), "user": response.json()}`. `payload` — исходный запрос с паролем; `user` — разобранный JSON ответа с серверными полями, включая ID (`registered_user["user"]["id"]`). Эти словари не смешиваются: при проверке дубликата отправляется копия `payload`, без ID и времени создания.
- `registered_login_data` зависит от `registered_user` и возвращает отдельный словарь email/password из `payload`. `disabled_user` использует того же зарегистрированного пользователя и отключает его по ID из `registered_user["user"]`.
- `user_access_token` подготавливает доступ обычного пользователя. В модуле профиля локальные фикстуры `profile_before` и `other_registered_user` готовят исходный профиль и второго пользователя для проверок конфликтов и изоляции.
- Фикстуры пользователей имеют стандартный scope function: отдельные тесты и варианты параметризации не используют одну изменяемую учётную запись.
- Новые похожие варианты одного правила добавляются в параметризацию. Сценарии с разными предусловиями и ожидаемым поведением остаются отдельными.
- Функции `register` и `login` поддерживают два способа отправки: `register(base_url, user_data)` отправляет словарь через `json=`, а `register(base_url, raw_body=body)` — исходный текст через `data=` с Content-Type application/json. В одном вызове выбирайте один способ. Пустая строка `raw_body=""` поддерживается. Тесты не формируют HTTP-запросы напрямую.
- Версии всех установленных зависимостей закреплены в requirements.txt. При обновлении зависимостей нужно выполнить полный прогон и обновить этот файл.

Тестовый стенд должен быть отдельным. Каждый успешный сценарий создаёт уникального пользователя; API не предоставляет удаление пользователей, поэтому записи после прогона остаются в БД. Очистка выполняется отдельно владельцем стенда по инструкции приложения; автотесты не сбрасывают БД. При долгой работе потребуется периодическое обновление тестового стенда.

При проверке негативного сценария отдельного поля проверяйте не только статус и общий код, но и соответствующее поле в `error.details`. Текст сообщения не фиксируется: он может уточняться. Для сломанного JSON не предполагается путь конкретного поля модели.

## Первый сценарий

Регистрация с уникальным email, валидными паролем и именем, без телефона.
Проверки: HTTP 201, значения email и name, phone = null, role = user,
is_active = true, отсутствие password и password_hash в ответе.

Фикстура `base_url` из `tests/conftest.py` передаст адрес API тесту, если указать `base_url` в аргументах тестовой функции.
