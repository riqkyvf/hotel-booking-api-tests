# Бизнес-правила

Нормативные подробности, включая порядок ошибок и конкурентные операции: [requirements.md](requirements.md). Этот документ фиксирует расчёт и граф состояний.

## Даты и суммы

Все даты и время относятся к UTC. `check_in` и `check_out` — календарные даты без времени. Интервал `[check_in, check_out)`. Длительность 1–14 ночей, заезд не в прошлом, гостей 1–10 и не больше вместимости. Цена положительна, не больше 9999999999.99 RUB; два знака после запятой. Цена с лишними значимыми десятичными знаками отклоняется, а не округляется.

`nights = (check_out - check_in).days`

`total_price = Decimal(price_per_night) * nights`

Стоимость хранится как снимок. Нет скидок, налоговых надбавок, доплат за гостей и конвертации валюты. Денежные значения JSON возвращаются десятичными строками, например `"3000.00"`.

## Доступность

Доступны только неархивные отели и номера с `is_available=true`, достаточной вместимостью и без блокирующих пересечений. Проверка доступности возвращает 200 с `available=false` и причиной `ROOM_DISABLED`, `CAPACITY_EXCEEDED` или `ROOM_NOT_AVAILABLE` в таком порядке. Некорректные даты дают 422, несуществующий/архивный номер — 404.

Удержание действует строго до `expires_at`. При `now >= expires_at` оно прекращается. Проверки и актуализация выполняются под блокировкой номера. Проверка доступности не даёт гарантии последующего бронирования.

Отключение новых бронирований не аннулирует уже созданные: их можно оплатить в пределах срока. Архивирование при действующих бронях запрещено.

## Переходы бронирования

| Из | В | Условие | Блокирует номер после перехода |
|---|---|---|---|
| отсутствует | pending_payment | Создание | Да |
| pending_payment | confirmed | Успех оплаты до срока | Да |
| pending_payment | expired | now >= expires_at | Нет |
| pending_payment | cancelled | Отмена до даты заезда | Нет |
| confirmed | cancelled | Отмена до даты заезда и полный возврат | Нет |
| confirmed | completed | UTC-дата >= check_out | Нет |

`cancelled`, `expired`, `completed` — конечные. Переходов обратно нет. Повтор отмены — чтение конечного состояния с 200.

## Переходы платежа

| Из | В | Условие |
|---|---|---|
| отсутствует | pending | Создание операции для ожидающей оплаты брони |
| pending | succeeded | Успешная симуляция |
| pending | failed | Отклонённая симуляция |
| pending | cancelled | Истечение или отмена брони |
| succeeded | refunded | Отмена оплаченной брони до заезда |

`failed`, `cancelled`, `refunded` — конечные. `succeeded` допускает только возврат. Повторные симуляции дают 409. После `failed` допускается новая операция с новым ID до исходного срока; старая операция не переиспользуется. Один `pending` и не более одной операции в `succeeded/refunded` на бронь обеспечиваются частичными уникальными индексами.

## Отмена и деактивация

Отмена только до даты заезда, полный тестовый возврат без комиссий, в одной транзакции с освобождением номера. Сам факт деактивации пользователя ничего не отменяет: неоплаченные брони истекают, оплаченные сохраняются, admin может отменить их по общим условиям. Повтор с тем же Idempotency-Key не создаёт новую бронь после отмены или истечения — он возвращает исторический ответ создания.

## Граница конкурентной операции

Решение принимается по `clock_timestamp()` после получения блокировок. Если оплату проверили до срока, коммит после срока допустим. Если блокировку получили в момент срока или позже, оплата запрещена. Изменение статуса брони, платежа и запись истории атомарны. Тайм-аут блокировки не означает успешное выполнение: ответ 409 `CONCURRENT_OPERATION` допускает повтор.
