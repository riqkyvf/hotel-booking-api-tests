# Работа тестов с PostgreSQL

Большинство сценариев готовит данные и проверяет результат через API. Прямой доступ к PostgreSQL нужен тестам с маркером `db`: для подготовки дат и проверки данных, которые не видны через HTTP. Подключение `TEST_DATABASE_URL` должно вести в ту же тестовую БД, что и API. [Настройки](../README.md#быстрый-старт)

## Подготовка дат

Функции в [db.py](../db.py) изменяют только даты брони конкретного тестового пользователя:

- `move_booking_expiry_to_past` переносит `expires_at` в прошлое, чтобы проверить истечение без ожидания 30 минут.
- `move_confirmed_booking_checkout_to_today` переносит проживание на день выезда по UTC, сохраняя число ночей и стоимость.

SQL не устанавливает итоговые статусы. Истечение, завершение проживания и связанные изменения платежей выполняет приложение; тест проверяет результат через API и при необходимости историю в БД.

## Проверка сохранённых данных

| Таблицы | Что проверяют тесты |
| --- | --- |
| `bookings`, `payments` | Принадлежность платежа брони, число записей и состояния после конкурентных запросов |
| `booking_status_history`, `payment_status_history` | Последовательность переходов, инициатора и отсутствие лишних событий |

Запросы чтения выполняются в режиме `read only`. Проверка истории помогает обнаружить повторную обработку операции, даже если итоговый статус выглядит правильным. [Конкурентные сценарии](testing-bookings.md#конкурентные-запросы)

## Связь с контрактом

Бронь хранит снимок цены; платёж связан с ней через `booking_id`. История содержит исходное и новое состояния и `actor_id` (`null` для системного перехода). [Расчёт стоимости и переходы состояний](business-rules.md)

Полное устройство приложения, миграции и обслуживание БД описаны в [репозитории API](https://github.com/riqkyvf/hotel-booking-api#readme).
