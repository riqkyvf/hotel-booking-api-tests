## Основной путь: выбор номера, бронирование и успешная оплата

Основания: [FR-04, FR-06 и FR-07](requirements.md#fr-04-бронирования), [контракт номеров, бронирований и платежей](api-specification.md#бронирования), [расчёт стоимости](business-rules.md#даты-и-суммы).

В этом этапе только три самостоятельных позитивных сценария. Каждый получает собственные отель, номер и при необходимости пользователя. Даты вычисляются от текущей UTC-даты; заезд через два дня, выезд через три ночи. Цена 1234.56 RUB за ночь позволяет проверить денежный расчёт без float. Создание отеля/номера через admin API — подготовка, а действия пользователя и проверки остаются в тестах.

| ID | Сценарий и шаги | Ожидаемые результаты | Статус | Автотест |
|---|---|---|---|---|
| BP-001 | Получить список номеров своего тестового отеля, открыть номер, проверить доступность на выбранные даты | Все ответы 200; в списке есть созданный номер; детали соответствуют отелю и данным подготовки; номер активен и не архивен; available=true, reason=null; правильные даты, гости, число ночей, сумма и RUB | Passed | [test_user_can_select_available_room](../tests/test_booking_flow.py) |
| BP-002 | Создать бронь с уникальным Idempotency-Key, прочитать её по ID и в списке пользователя | 201 и pending_payment; корректные UUID пользователя/номера, даты и гости; цена и итог рассчитаны сервером, итог = 1234.56 × 3 = 3703.68 RUB; expires_at в будущем; GET подтверждает сохранение; список содержит единственную собственную бронь | Passed | [test_user_can_create_and_read_booking](../tests/test_booking_flow.py) |
| BP-003 | Создать бронь, создать платёж, симулировать успех и прочитать оба ресурса | Бронь сначала pending_payment; платёж создаётся с 201/pending, правильными booking_id, суммой и валютой; симуляция возвращает 200/succeeded; GET платежа подтверждает succeeded, GET брони — confirmed; IDs, владелец, даты, гости и суммы сохранены | Passed | [test_user_can_pay_for_booking](../tests/test_booking_flow.py) |

<a id="booking-payment-checklist-границы-этапа"></a>

### Границы этапа

- Не проверяются отмена/возврат, отказы оплаты, пересечения, повторные запросы, чужие ресурсы, полные матрицы валидации и конкурентные операции. Это следующие приоритетные сценарии, а не забытые проверки.
- Наличие корректного будущего expires_at проверяется без ожидания; точные временные границы и истечение удержания остаются отдельным этапом.
- Платежи тестовые: реальных списаний нет. Состояния и суммы проверяются через HTTP API, без SQL.
- Данные не удаляются; используются только собственные новые ресурсы. Изменения приложения при найденных дефектах не выполняются.

## Ограничения создания брони

Основания: [FR-04](requirements.md#fr-04-бронирования), [даты и доступность](business-rules.md), [коды ошибок](api-specification.md).

| ID | Проверка | Ожидаемый результат | Статус |
|---|---|---|---|
| BR-001 | Заезд вчера по UTC, длительность допустима | 422 PAST_CHECK_IN; бронь не создаётся | Passed |
| BR-002 | Выезд в день заезда | 422 VALIDATION_ERROR, ошибка тела запроса; бронь не создаётся | Passed |
| BR-003 | Выезд раньше заезда | 422 VALIDATION_ERROR, ошибка тела запроса; бронь не создаётся | Passed |
| BR-004 | Гостей на одного больше вместимости номера, но в допустимых пределах 1–10 | availability: 200, available=false, reason=CAPACITY_EXCEEDED; POST: 409 CAPACITY_EXCEEDED; бронь не создаётся | Passed |
| BR-005 | Номер отключён администратором | availability: 200, available=false, reason=ROOM_DISABLED; POST: 409 ROOM_DISABLED; бронь не создаётся, номер остаётся отключённым | Passed |
| BR-006 | Номер архивирован администратором | availability и POST: 404 NOT_FOUND; бронь не создаётся | Passed |
| BR-007 | Заезд сегодня по UTC, обычная длительность | availability: available=true; создание 201 pending_payment; правильные даты, владелец, число ночей и сумма; GET подтверждает сохранение | Passed |
| BR-008 | Проживание 1 ночь с будущим заездом | Те же успешные результаты; сумма за одну ночь | Passed |
| BR-009 | Проживание 14 ночей с будущим заездом | Те же успешные результаты; сумма за 14 ночей | Passed |
| BR-010 | Проживание 15 ночей с будущим заездом | availability и POST: 422 VALIDATION_ERROR; ошибка POST относится к телу; бронь не создаётся | Passed |

BR-007–010 добавлены в чек-лист до реализации. Для допустимых интервалов проверяются доступность до создания, точные дата заезда/выезда, число ночей и сумма через Decimal, затем создание, GET и единственная бронь в списке владельца. Сегодня вычисляется по UTC при подготовке запроса; ожидания и подмена времени не используются.

После каждого отклонённого POST список собственного уникального пользователя содержит total=0 и items=[]. Для POST-ошибок проверяются ERROR_SCHEMA, код и совпадение request ID. Каждый случай создаёт собственный отель и номер; остальные входные данные валидны. Для BR-001 вчера определяется относительно UTC при подготовке запроса; для BR-002–006 используется будущий интервал общей фикстуры; BR-007–010 задают границы отдельно. Каждый POST получает отдельный Idempotency-Key.

Границы: это основные бизнес-ограничения, без полной матрицы типов и пропущенных полей, архивного отеля и сочетаний нескольких ошибок. Верхняя длительность проверяется на 14 и 15 ночах, без перебора всех больших значений. SQL и ожидания не используются. Ожидания не подстраиваются под дефекты приложения.

## Пересечение дат бронирования

Основания: [FR-04](requirements.md#fr-04-бронирования), [доступность и состояния](business-rules.md), [ошибки API](api-specification.md).

Каждый случай создаёт собственный номер, бронь первого пользователя и второго пользователя. Проверки выполняются для pending_payment и confirmed. Для confirmed используется успешная тестовая оплата через API. Каждый POST получает новый Idempotency-Key. Даты рассчитываются от UTC; SQL и ожидание истечения не используются.

| ID | Проверка | Ожидаемый результат | Статус |
|---|---|---|---|
| BO-001 | Полное совпадение интервалов | availability: 200, available=false, reason=ROOM_NOT_AVAILABLE; создание: 409 ROOM_NOT_AVAILABLE | Passed |
| BO-002 | Частичное пересечение слева | Те же отказы доступности и создания | Passed |
| BO-003 | Частичное пересечение справа | Те же отказы доступности и создания | Passed |
| BO-004 | Новый интервал внутри существующего | Те же отказы доступности и создания | Passed |
| BO-005 | Новый интервал охватывает существующий | Те же отказы доступности и создания | Passed |
| BO-006 | Выезд новой брони совпадает с заездом существующей | available=true, reason=null; создание 201 pending_payment, корректные номер, даты и владелец | Passed |
| BO-007 | Заезд новой брони совпадает с выездом существующей | available=true, reason=null; создание 201 pending_payment, корректные номер, даты и владелец | Passed |
| BO-008 | Другой физический номер того же отеля на те же даты | available=true, reason=null; создание 201 pending_payment, корректные номер, даты и владелец | Passed |

После отказа проверяются отсутствие брони у второго пользователя и сохранность исходной брони. После успешного создания читаются обе брони: первая сохраняется, новая содержит ожидаемые данные. Проверяется единый формат ошибки 409 и request ID.

Это последовательные проверки пересечений. Конкурентные запросы, отмена и истечение удержания остаются отдельными этапами. При несоответствии требованиям тест должен падать; приложение не исправляется ради зелёного результата.

## Отмена брони и освобождение номера

Основания: [FR-08](requirements.md#fr-08-отмена), [контракт бронирований](api-specification.md#бронирования), [состояния](business-rules.md).

| ID | Сценарий | Ожидаемый результат | Статус |
|---|---|---|---|
| BC-001 | Владелец отменяет будущую pending_payment-бронь без платежа | PATCH 200, cancelled; GET подтверждает статус и сохранность данных; номер доступен на исходные даты; второй пользователь создаёт новую бронь | Passed |
| BC-002 | Владелец отменяет будущую pending_payment-бронь с pending-платежом | Те же результаты; платёж становится cancelled, сумма, валюта и связь с бронью сохраняются | Passed |
| BC-003 | Владелец отменяет будущую confirmed-бронь после успешной оплаты | Те же результаты; платёж становится refunded с сохранением полной суммы и валюты | Passed |
| BC-004 | Повторная отмена будущей брони без платежа | 200 с тем же cancelled-ресурсом; GET подтверждает сохранение; номер остаётся доступен | Passed |
| BC-005 | Повторная отмена будущей брони с pending-платежом | То же; после первой отмены платёж cancelled и после повтора не меняется | Passed |
| BC-006 | Повторная отмена оплаченной будущей брони | То же; после первой отмены платёж refunded, сумма и весь ресурс после повтора не меняются | Passed |
| BC-007 | Отмена pending_payment-брони с заездом сегодня по UTC | 409 CANCELLATION_CLOSED; бронь и pending-платёж не меняются, номер занят | Passed |
| BC-008 | Отмена confirmed-брони с заездом сегодня по UTC | 409 CANCELLATION_CLOSED; бронь и succeeded-платёж не меняются, номер занят | Passed |

До отмены проверяется недоступность исходного интервала. После отмены повторное бронирование выполняется другим пользователем с новым Idempotency-Key; GET новой брони подтверждает даты, номер и владельца, а старая остаётся cancelled. Проверяется X-Request-ID ответа отмены. Тесты используют собственные ресурсы, будущие даты UTC и тестовые платежи; очистка через SQL не выполняется.

BC-004–008 добавлены в чек-лист до расширения тестов. Повторная отмена проверяется в будущем интервале; для запрета используются брони, созданные в текущую UTC-дату заезда, без ожиданий. Число возвратов в БД не проверяется: API не предоставляет историю возвратов; проверяются неизменность refunded-платежа, его суммы и временных полей.

Границы этапа: отмена владельцем до заезда и запрет отмены в день заезда. Чужая бронь покрыта в чек-листе доступа. Права admin, повтор отмены после наступления даты заезда, expired/completed и конкурентные операции остаются отдельными проверками. Несоответствия приложения фиксируются как дефекты.

## Истечение удержания: подготовка через SQL

Основания: [FR-05](requirements.md#fr-05-точное-истечение), [FR-07](requirements.md#fr-07-тестовые-платежи), [доступность и состояния](business-rules.md).

| ID | Проверка | Ожидаемый результат | Статус |
|---|---|---|---|
| BE-001 | Создать бронь и pending-платёж через API, перенести expires_at своей брони в прошлое через SQL, попытаться оплатить, прочитать ресурсы и забронировать освободившийся номер вторым пользователем | До SQL номер занят. Оплата: 409 BOOKING_EXPIRED; GET брони: expired с установленным expires_at; GET платежа: cancelled; данные, суммы и связь с бронью сохранены. Новый платёж для истёкшей брони: 409 BOOKING_EXPIRED. Доступность: true; новая бронь другого пользователя: 201 pending_payment с теми же номером и датами; исходная бронь остаётся expired | Passed |

Одна функция db.py выполняет параметризованный UPDATE только expires_at для ID брони, user_id и status=pending_payment, возвращает установленную дату и фиксирует транзакцию до следующего HTTP-запроса. Серверное clock_timestamp() минус одна минута исключает зависимость SQL-подготовки от часов клиента. Статусы и платёж тест через SQL не меняет; их актуализируют приложение или worker. Если строка не найдена, подготовка завершается ошибкой.

TEST_DATABASE_URL должен указывать на ту же отдельную тестовую БД, которую использует API. Настройка обязательна для этого теста; при её отсутствии тест падает с понятным сообщением, а не пропускается. Метка db позволяет запускать или исключать такие сценарии. Пароль хранится в локальном .env или окружении CI; в .env.example приведены только демонстрационные параметры стенда.

Границы: проверка обработки уже истёкшего удержания и сохранения переходов после ошибочного HTTP-ответа. Не доказывает длительность удержания 30 минут, срабатывание worker без API-запросов или точное равенство now=expires_at. Нет ожиданий, подмены системного времени, ручного изменения статусов и очистки БД. Будущие даты и собственные ресурсы сохраняют изоляцию от других тестов.

## Доступ к чужим бронированиям и платежам

Основания: [FR-04](requirements.md#fr-04-бронирования), [FR-07](requirements.md#fr-07-тестовые-платежи), [FR-08](requirements.md#fr-08-отмена), [ошибки API](api-specification.md). Для чужих приватных ресурсов контракт требует 404 NOT_FOUND независимо от состояния.

| ID | Проверка | Ожидаемый результат | Статус |
|---|---|---|---|
| BA-001 | Второй пользователь читает чужую бронь по известному ID | 404 NOT_FOUND; чужой брони нет в его списке; владелец читает неизменённую бронь | Passed |
| BA-002 | Второй пользователь отменяет чужую будущую бронь | 404 NOT_FOUND; владелец видит исходные бронь и платёж без изменений; номер остаётся занят | Passed |
| BA-003 | Второй пользователь читает чужой платёж по известному ID | 404 NOT_FOUND; владелец читает неизменённые платёж и бронь | Passed |
| BA-004 | Второй пользователь создаёт платёж для чужой брони без платежа | 404 NOT_FOUND; бронь сохранена; владелец затем успешно создаёт собственный pending-платёж | Passed |
| BA-005 | Второй пользователь симулирует успех чужого платежа | 404 NOT_FOUND; исходные платёж и бронь сохранены | Passed |
| BA-006 | Второй пользователь симулирует отказ чужого платежа | 404 NOT_FOUND; статус и failure_reason платежа, данные брони сохранены | Passed |

BA-001/002/003/005/006 выполняются для двух состояний: pending_payment с pending-платежом и confirmed с succeeded-платежом — 10 случаев. BA-004 выполняется для pending_payment-брони без платежа, ещё один случай. Всего 11 случаев доступа. Новые BA-004/005/006 добавлены в чек-лист до реализации. В ответах отказа проверяются ERROR_SCHEMA, код и совпадение X-Request-ID с error.request_id. Два пользователя регистрируются независимо, ID ресурса реально существует и заранее проверен владельцем.

Каждый случай создаёт собственные ресурсы через API и использует будущие даты UTC. SQL, ожидание истечения, динамический выбор API-методов и общие изменяемые ресурсы не используются. Права admin описаны в [отдельном чек-листе](testing-bookings.md#admin-booking-access-checklist); отсутствие токена остаётся отдельным этапом. В BA-004 отсутствие созданного чужим пользователем pending-платежа дополнительно проверяется успешным созданием платежа владельцем; прямой подсчёт записей БД не выполняется. Приложение при выявлении дефектов не исправляется ради зелёного прогона.
