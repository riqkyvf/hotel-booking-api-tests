# Бронирование и платежи

Контракт: [операции бронирований и платежей](api-specification.md#бронирования), [бизнес-правила](business-rules.md). Сценарии с меткой `db` используют PostgreSQL для подготовки дат и проверки сохранённых состояний. Статусы меняет приложение. [Настройки подключения](../README.md#быстрый-старт)

<a id="booking-payment-checklist"></a>

## Основной путь

[Основной путь](../tests/test_booking_flow.py) проверяет выбор доступного номера, создание и чтение брони, расчёт суммы и успешную оплату. Состояния после оплаты — `confirmed` и `succeeded`.

<a id="booking-restrictions-checklist"></a>

## Ограничения и доступность

[Ограничения](../tests/test_booking_restrictions.py) проверяют даты, вместимость и состояние номера при создании. [Валидация брони](../tests/test_booking_validation.py) проверяет типы, границы и ошибки JSON.

<a id="room-availability"></a>

[Доступность](../tests/test_room_availability.py) проверяет обязательные параметры, границы дат и числа гостей, расчёт стоимости, порядок причин отказа, архивный номер и освобождение интервала после истечения удержания. Запрос доступности сам не резервирует номер.

<a id="booking-overlap-checklist"></a>

[Пересечения](../tests/test_booking_overlap.py) проверяют запрет совпадающих и частично пересекающихся дат для `pending_payment` и `confirmed`. Соседние интервалы и бронь другого номера разрешены.

<a id="booking-access-checklist"></a>

## Доступ к броням и платежам

[Изоляция пользователей](../tests/test_booking_access.py) проверяет, что чужой пользователь не может прочитать бронь или платёж, отменить бронь или выполнить платёжную операцию.

<a id="admin-booking-access-checklist"></a>

[Права администратора](../tests/test_admin_booking_access.py) допускают чтение чужих ресурсов и отмену чужой брони. Создание и симуляция чужого платежа отклоняются.

<a id="booking-list"></a>

## Список и детали

[Список](../tests/test_booking_list.py) проверяет фильтры, сортировку, пагинацию и изоляцию владельцев. Обычный пользователь получает `403` с любым `user_id`, даже собственным. Фильтр `expired` проверяется на существующей истёкшей брони и на пустой выборке. Фильтр `completed` покрыт сценарием завершения проживания.

Для владельца проверяются отдельные фильтры и их сочетания. Для администратора есть отдельный сценарий с `user_id`, отелем и статусом, а также сортировка по убыванию цены. Обе роли проходят две страницы и пустую выдачу с проверкой порядка и границ `limit`.

<a id="booking-payment-reading"></a>

[Детали брони и платежа](../tests/test_booking_payment_reading.py) проверяются для владельца и администратора в нескольких состояниях. Тесты валидируют JSON Schema и форматы, суммы и связь платежа с бронью. Для `422` используется один неверный UUID на операцию. Неизвестный UUID даёт `404` для обеих ролей.

<a id="booking-payment-mutation-ids"></a>

## UUID в изменяющих запросах

[Тесты](../tests/test_booking_payment_ids.py) покрывают отмену брони, создание платежа и обе симуляции. Строка `not-a-uuid` даёт `422 VALIDATION_ERROR` с полем `path.booking_id` или `path.payment_id`. Корректный UUID отсутствующей записи даёт `404 NOT_FOUND`. Во всех случаях проверяются схема ошибки и `X-Request-ID`.

<a id="booking-cancellation-checklist"></a>

## Отмена, истечение и завершение

[Отмена](../tests/test_booking_cancellation.py) проверяет освобождение дат, повтор операции, отмену ожидающего платежа, возврат успешного платежа и запрет отмены в день заезда.

<a id="booking-expiration-checklist"></a>

[Тест истечения](../tests/test_booking_expiration.py) сдвигает срок удержания в прошлое и проверяет отказ в оплате, статус `expired` у брони, отмену ожидающего платежа и освобождение дат. Фоновый процесс может применить переходы до запроса оплаты.

<a id="booking-completion"></a>

[Завершение проживания](../tests/test_booking_completion.py) проверяет переход в `completed` в день выезда по UTC, сохранение успешного платежа, запрет отмены и платёжных операций, фильтр списка и повтор исходного ключа. SQL сдвигает даты с сохранением числа ночей. История подтверждает один переход и отсутствие лишних событий платежа.

<a id="room-booking-integrity"></a>

## Изменение номера при действующей брони

[Целостность брони](../tests/test_room_booking_integrity.py) проверяет запрет архивации и снижения вместимости ниже числа гостей. Изменение цены действует на новые брони, а прежняя хранит исходную сумму. Отключение номера не мешает оплатить уже созданную бронь.

<a id="payment-failure-checklist"></a>

## Отказ оплаты и повторные запросы

[Отказ оплаты](../tests/test_payment_failure.py) сохраняет удержание и допускает новую попытку с другим ID. [Валидация отказа](../tests/test_payment_validation.py) проверяет поле `reason` и ошибки тела.

<a id="repeated-requests-checklist"></a>

[Повторы бронирования](../tests/test_booking_idempotency.py) проверяют возврат исходного ответа с тем же ключом и телом, конфликт при изменении тела и отсутствие дублей после оплаты, отмены или истечения. Для истёкшей брони повтор возвращает исходный `201` и прежний `Location` с `Idempotency-Replayed: true`. В списке остаётся одна бронь со статусом `expired`, а `expires_at` не меняется. [Повторы платежей](../tests/test_payment_repeated_requests.py) проверяют конфликты повторного создания и симуляции.

<a id="booking-payment-gaps"></a>

[Область ключа](../tests/test_booking_validation.py) проверяется между пользователями. [Матрица состояний](../tests/test_booking_payment_states.py) проверяет запреты для подтверждённых, отменённых и истёкших броней.

## Конкурентные запросы

Два потока ждут друг друга перед отправкой запросов (`Barrier`). Тест проверяет ответы и сохранённые данные для того порядка, который произошёл в этом запуске. Момент начала транзакций на сервере может различаться.

<a id="booking-concurrency"></a>

- **CON-001. Разные ключи, один номер и даты.** Один запрос создаёт бронь, второй получает `409 ROOM_NOT_AVAILABLE`. Списки владельцев и администратора подтверждают единственную бронь. [Тест](../tests/test_booking_concurrency.py)

<a id="concurrent-idempotency"></a>

- **CON-002. Одинаковый ключ и тело.** Два ответа `201` содержат одну бронь и одинаковый `Location`. Только один помечен `Idempotency-Replayed: true`. [Тест](../tests/test_booking_concurrency.py)

<a id="payment-concurrency"></a>

- **CON-003. Два создания платежа.** Один `201`, второй `409 PAYMENT_ALREADY_PENDING`. SQL подтверждает единственную запись платежа. [Тест](../tests/test_payment_concurrency.py)

<a id="payment-success-concurrency"></a>

- **CON-004. Две успешные симуляции одного платежа.** Один `200`, второй `409 BOOKING_NOT_PAYABLE`. История содержит по одному переходу в `succeeded` и `confirmed`. [Тест](../tests/test_payment_concurrency.py)

<a id="payment-cancellation-concurrency"></a>

- **CON-005. Оплата против отмены.** Отмена всегда возвращает `200`. При оплате первой итоговый платёж `refunded`. При отмене первой оплата получает `409 BOOKING_NOT_PAYABLE`, платёж остаётся `cancelled`. Тест проверяет освобождение номера, одну строку платежа и историю переходов. Наблюдавшийся порядок записывается в JUnit как `payment_cancellation_outcome`. [Тест](../tests/test_payment_concurrency.py)
