# Права администратора на чужие брони и платежи

Дата: 03.11.2026. Чек-лист составлен до реализации. HTTP-прогон всех девяти модулей бронирования и платежей: **67 passed за 69.69 с**, включая 9 новых случаев admin. Отчёт `junit-admin-booking-access.xml` исключён из Git. Полный набор содержит 500 случаев; после добавления этих сценариев полный HTTP-прогон не повторялся.

Основания: [общий контракт ролей](api-specification.md#общий-контракт), [FR-04](requirements.md#fr-04-бронирования), [FR-07](requirements.md#fr-07-тестовые-платежи), [FR-08](requirements.md#fr-08-отмена).

| ID | Проверка | Ожидаемый результат | Статус |
|---|---|---|---|
| AA-001 | Admin читает чужую бронь и платёж, запрашивает список с user_id владельца | 200, точные сохранённые данные; список содержит единственную бронь владельца; данные при чтении не меняются | Passed |
| AA-002 | Admin отменяет чужую будущую бронь | 200 cancelled; pending-платёж становится cancelled, succeeded — refunded; владелец читает актуальные данные; номер доступен | Passed |
| AA-003 | Admin создаёт платёж для чужой брони без платежа | 404 NOT_FOUND; бронь не меняется; владелец затем успешно создаёт pending-платёж | Passed |
| AA-004 | Admin симулирует успех чужого платежа | 404 NOT_FOUND; бронь и платёж не меняются | Passed |
| AA-005 | Admin симулирует отказ чужого платежа | 404 NOT_FOUND; бронь и платёж, включая failure_reason, не меняются | Passed |

AA-001/002/004/005 выполняются для pending_payment + pending и confirmed + succeeded, AA-003 — для pending_payment без платежа. Всего 9 случаев. Администратор использует отдельную учётную запись из окружения; владелец — новый пользователь, созданный тестом. Перед действиями admin владелец получает ресурсы через GET, подтверждая существование и исходные состояния. Для AA-003 исходная бронь подтверждена ответом создания.

Для отказов проверяются ERROR_SCHEMA, NOT_FOUND и совпадение X-Request-ID. После отмены проверяются сохранность идентификаторов, владельца, дат и сумм, сохранение статусов через GET владельца и освобождение номера. Для чтения списка применяется уникальный user_id; глобальное число броней стенда не предполагается.

Границы: обычные последовательные запросы, будущий заезд UTC, собственные ресурсы. Полная матрица admin-фильтров, создание брони администратором для себя, границы отмены и конкурентные операции не входят в этот блок. Нет SQL и ожиданий. HTTP не предоставляет историю возвратов и список платежей: прямой подсчёт записей не выполняется.
