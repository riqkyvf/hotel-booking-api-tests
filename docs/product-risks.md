## Риски и выбранные проверки

Приоритет определяется последствиями для гостей, отеля и данных. **В** означает высокий приоритет, **С** — средний. Вероятность не оценивалась. FR указывает источник правила в требованиях. Карта отражает реализованные сценарии. Результаты прогонов доступны в [CI](https://github.com/riqkyvf/hotel-booking-api-tests/actions/workflows/api-tests.yml).

### Основные риски

| Риск и последствия | Что проверяется и почему |
| --- | --- |
| **R-01 · В. Нарушение доступа.** Пользователь видит чужие данные или выполняет запрещённое действие. FR-01–02, 04, 07–08. | Без действительного токена защищённая операция возвращает `401`. Административная операция для обычного пользователя даёт `403`, действие без права на чужую бронь или платёж — `404`. Для одного пользователя действующий JWT открывает профиль, а просроченный с корректной подписью даёт `401`. Отдельно проверяются права администратора и смена роли при прежнем токене. [Истечение JWT](../tests/auth/test_token_expiration.py#L26) · [Другие ошибки JWT](../tests/auth/test_authorization.py) · [Роли](../tests/users/test_admin_users.py#L109) · [Административные операции](../tests/auth/test_admin_operations_access.py) · [Чужая бронь и платёж](../tests/bookings/test_booking_access.py) · [Права администратора](../tests/bookings/test_admin_booking_access.py) |
| **R-02 · В. Двойное бронирование.** Один номер обещан нескольким гостям. FR-04, 09. | Даты действующей брони нельзя занять повторно, а смежные даты или другой номер доступны. При параллельной отправке двух запросов проверяется один успех, один `409 ROOM_NOT_AVAILABLE` и одна сохранённая бронь. [Интервалы](../tests/bookings/test_booking_overlap.py) · [Параллельное создание](../tests/bookings/test_booking_concurrency.py#L14)<br>**Ограничение.** Одновременная отправка запросов не гарантирует, что их обработка на сервере пересечётся. |
| **R-03 · В. Сбой оплаты или отмены.** Неверная сумма, статус или возврат. FR-07–09. | Проверяются сумма и подтверждение брони после оплаты, сохранение удержания при отказе и освобождение дат при отмене. Ожидающий платёж отменяется, успешный получает статус `refunded`. История в БД выявляет повторные переходы. [Оплата](../tests/bookings/test_booking_flow.py#L118) · [Отказ и новая попытка](../tests/payments/test_payment_failure.py) · [Отмена](../tests/bookings/test_booking_cancellation.py) · [Конкуренция платежей](../tests/payments/test_payment_concurrency.py)<br>**Ограничение.** В проверке оплаты и отмены за один прогон проверяется тот порядок операций, который сложился на сервере. |
| **R-04 · В. Ошибка срока оплаты.** Просроченная бронь оплачивается или своевременная оплата отклоняется. FR-05, 07. | Для новой брони сверяется срок удержания в 30 минут с допуском ±5 с относительно окна HTTP-запроса. При оплате после срока проверяются `409 BOOKING_EXPIRED`, сохранённые статусы и освобождение дат. [Срок удержания](../tests/bookings/test_booking_flow.py#L61) · [Истечение](../tests/bookings/test_booking_expiration.py) · [Доступность](../tests/rooms/test_room_availability.py)<br>**Ограничение.** Точная граница срока и ожидание блокировки вне покрытия. |
| **R-05 · В. Дубли при повторе запроса.** Возникает вторая бронь или продлевается удержание. FR-06, 09. | Тот же ключ и те же валидные данные дают исходный ответ `201` без новой брони и продления срока. Другие валидные данные с тем же ключом дают `409`. Проверяются независимость ключей разных пользователей и параллельный повтор. [Повторы](../tests/bookings/test_booking_idempotency.py) · [Область ключа](../tests/bookings/test_booking_validation.py#L92) · [Параллельный повтор](../tests/bookings/test_booking_concurrency.py#L87) |

## Состояния брони

| Переход | Что происходит |
| --- | --- |
| Создание → `pending_payment` | Даты временно удерживаются, пока бронь ждёт оплаты |
| `pending_payment` → `confirmed` | Платёж успешен, даты остаются занятыми |
| `pending_payment` → `expired` | Срок вышел, ожидающий платёж отменяется, даты освобождаются |
| `pending_payment` / `confirmed` → `cancelled` | До даты заезда по UTC. Ожидающий платёж отменяется, успешный возвращается, даты освобождаются |
| `confirmed` → `completed` | Наступила дата выезда по UTC, платёж остаётся успешным |

## Границы покрытия

Набор проверяет поведение HTTP API. В части сценариев дополнительно сверяются сохранённые данные и история в PostgreSQL.

**R-11 · В. Потеря данных при эксплуатации.** Сохранность данных при перезапуске или миграции, восстановление после сбоя, атомарность начального заполнения и безопасный сброс базы вне текущего набора. [Требования FR-10](https://github.com/riqkyvf/hotel-booking-api/blob/0d8396f38c8a7b727648585e33b3d34fe54652ab/docs/requirements.md#fr-10-контракт-и-эксплуатация) · [Эксплуатация приложения](https://github.com/riqkyvf/hotel-booking-api/tree/0d8396f38c8a7b727648585e33b3d34fe54652ab)

Вне набора остаются нагрузка, защита от перебора и управление ключами JWT. Платежи в API имитируются.
