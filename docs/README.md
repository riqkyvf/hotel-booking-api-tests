## Карта покрытия API

Состояние на 03.11.2026. Основание — [29 операций спецификации](api-specification.md), фактические вызовы и проверки в `tests/`, включая фикстуры. Общий префикс путей — `/api/v1`. Карта составлена чтением кода; новый HTTP-прогон для неё не выполнялся. Последний результат набора — в [журнале](test-runs.md).

Обозначения:

- **Сценарии** — есть развёрнутый набор позитивных и негативных проверок операции или её бизнес-переходов. Это не означает полного покрытия контракта.
- **Частично** — проверяются отдельные ответы, права или шаги сквозного сценария; существенные части операции ещё не проверены.
- **Подготовка** — основной сценарий операции создаёт нужное состояние для проверки другой функции продукта; успех подготовки проверяется, самостоятельной матрицы операции нет; отдельные общие проверки авторизации отмечены в строке.
- **Нет** — автоматических вызовов и проверок операции в наборе не найдено. Инструкция ручного вызова в README не считается автотестом.

### Итог и следующие задачи

Из 29 операций: **26 — «Сценарии», 1 — «Частично», 0 — «Подготовка», 2 — «Нет»**. Это распределение глубины проверок, а не процент покрытия требований, ветвей кода или готовности продукта. Даже наличие API-функции или успешного вызова в фикстуре не означает самостоятельного покрытия эндпоинта.

Следующие задачи после отсутствующего/пустого токена бронирований и платежей (04.11.2026: 14 новых и 32 связанных случая прошли вместе, 46 passed за 38.19 с; полный прогон не выполнялся):

1. Отсутствующий заголовок и пустой Bearer дополнены для всех операций бронирований/платежей. Дополнительные форматы/подпись JWT на этих ручках остаются пробелом; сейчас не расширялись по решению владельца. Отсутствующий/пустой/сломанный токен и повреждённая подпись уже проверены на профиле, списке бронирований и создании отеля. Истечение и неверные iss/aud отложены владельцем; см. [границы проверок](testing-auth.md#authorization).
2. Запрет административных операций обычному пользователю с действующим JWT добавлен для 10 операций (14 случаев). Создание, список и детали номеров дополнены 87 случаями. Изменение, включение/отключение и архивирование дополнены 86 случаями; оставшиеся ограничения указаны в строках карты. Использовать контракт [номеров](api-specification.md#номера).
3. Администрирование пользователей дополнено 50 случаями и тремя изолированными проверками последнего admin. Дальнейший пробел — конкурентные изменения; общий стенд для LAST_ACTIVE_ADMIN не используется.
4. Управление отелями дополнено 103 случаями. Список бронирований дополнен самостоятельными фильтрами, сортировками, пагинацией и проверками ролей; запрос доступности дополнен 53 случаями; детали брони/платежа дополнены UUID и схемами (44 случая); следующие крупные пробелы — health и отложенные сценарии. Валидация бронирований/отказа оплаты и матрица confirmed/cancelled/expired дополнены 71 случаем; оставшиеся пробелы перечислены в строках операций.
5. Health — небольшой отдельный блок; конкурентные операции и точные временные границы — после стабилизации последовательных сценариев.

При изменении тестов обновлять соответствующую строку карты и подробные сценарии по теме. Статус повышается по фактическим проверкам, а результат прогона фиксируется отдельно в журнале.

Приложение находится в отдельном репозитории [Hotel Booking API](https://github.com/riqkyvf/hotel-booking-api). В репозитории автотестов нет `compose.yaml`, Dockerfile и исходников приложения. Нужен запущенный Docker Desktop с Linux containers.

Из каталога, где вы храните проекты, выполните:

```powershell
git clone https://github.com/riqkyvf/hotel-booking-api.git
Set-Location hotel-booking-api
docker compose up --build -d
docker compose ps -a
Invoke-RestMethod http://localhost:8000/api/v1/health/ready
git rev-parse HEAD
```

Если приложение уже клонировано, перейдите в его каталог с `compose.yaml` и запускайте команды оттуда. Дождитесь HTTP 200 и `status = ready`; если init ещё работает, повторите проверку после его завершения. Сохраните commit приложения вместе с результатом прогона. Исторический commit приложения для результата от 01.11.2026 не был зафиксирован; совместимость новой версии подтверждается отдельным прогоном.

После подготовки стенда вернитесь в каталог автотестов и следуйте основному README. `.env` приложения и `.env` автотестов — разные файлы: первый настраивает сервер, второй — адрес API и учётные данные для тестов. Для локального запуска приложение имеет свои демонстрационные настройки по умолчанию.

При изменении `.env` приложения используйте свои значения. JDBC URL: `jdbc:postgresql://localhost:5433/hotel`. Схема `public`. Для времён UTC выполните `SET TIME ZONE 'UTC'` в нужной SQL-сессии.

## Seed и сброс

Учётные записи: admin@example.com, admin2@example.com, alice@example.com, bob@example.com, disabled@example.com. Общий локальный пароль `HotelDemo123!`; последняя учётная запись неактивна. При первом старте seed выполняется автоматически, повторный запуск не изменяет данные.

Сброс без публичного HTTP-эндпоинта; владелец отдельного тестового стенда выполняет команды из корня **репозитория приложения**, где лежит `compose.yaml`. Команды удаляют все данные приложения; во время сброса тесты и другие пользователи стенда работать не должны:

```powershell
docker compose stop api worker
docker compose run --rm --no-deps api python -m app.scripts.reset_db --confirm-reset
docker compose up -d
```

## Диагностика

Все Docker-команды выполняются в репозитории приложения. `docker compose ps -a` показывает `db/api/worker` healthy и `init` exited (0). При проблемах используйте `docker compose logs --tail 100 init api worker db`. Проверка миграции: `docker compose exec api alembic current`, сверка моделей: `docker compose exec api alembic check`.

Worker повторяет проход через 5 секунд; healthcheck считает его готовым, если успешный проход был менее 60 секунд назад. Ошибки пишутся в stdout/stderr контейнеров. API возвращает request_id для сопоставления ошибок с журналом; секреты не включаются в ответы об ошибках.

Неоплаченные seed-брони меняют состояние со временем — это нормальное поведение. Точность проверки срока не зависит от частоты worker: API сверяет `clock_timestamp()` после получения блокировок.
