## Версия приложения и ожидаемое поведение

Приложение `hotel-booking-api` находится в отдельном репозитории. В текущем workflow тестов шаг `Check out API` закреплён на коммите `0d8396f38c8a7b727648585e33b3d34fe54652ab`. Все тематические матрицы покрытия ссылаются на требования и REST-спецификацию этого коммита; общая документация также содержит ссылки на `main`, который может описывать более позднюю версию. При расхождении ожиданий с результатом существенна версия именно проверяемого приложения; наличие ссылки на `main` не доказывает дефект закреплённой версии.

Источники: [workflow, шаг Check out API](../.github/workflows/api-tests.yml), [контракт и ссылки на первоисточники](README.md#контракт). Коммит применим к текущему workflow; при его изменении запись требует сверки.

Сверка двух документов контракта 2026-11-16: в `main` на коммите `d70a50c7dd6d3febe134010b5cb4a9c8cddb7089` относительно версии CI добавлены явные уточнения ценового поиска отелей. Один включённый неархивный номер должен удовлетворять обеим границам фильтра; сортировка использует минимум всех включённых неархивных номеров, независимо от диапазона; отели без цены идут последними при обоих направлениях. Границы ценового фильтра — 0–9999999999.99. Других текстовых различий в этих двух документах при сверке не обнаружено. Локальная матрица HCL-009/012/013/017 уже содержит эти детали, но её ссылки закреплены на прежнем коммите; это различие явности источников, а не подтверждение изменения поведения API. Источники: [FR-03 новой версии](https://github.com/riqkyvf/hotel-booking-api/blob/d70a50c7dd6d3febe134010b5cb4a9c8cddb7089/docs/requirements.md#fr-03-каталог), [REST новой версии](https://github.com/riqkyvf/hotel-booking-api/blob/d70a50c7dd6d3febe134010b5cb4a9c8cddb7089/docs/api-specification.md#отели), [локальная матрица](testing-hotels.md#hotels-checklist). Реализация и работающий API в этой сверке не анализировались.

## Изоляция проверок последнего активного администратора

Подготовка этих проверок понижает роли остальных активных администраторов, чтобы оставить одного. Это причина отдельного запуска: локальный runner создаёт временные API и PostgreSQL и запрашивает удаление своих контейнеров и сети в `finally`. Он использует уже собранный образ `hotel-booking-api`; обычный локальный стенд для этой подготовки не предназначен.

В режиме `--reuse-ci-stand` runner использует одноразовый стенд финальной фазы `full`. Код проверяет GitHub-hosted окружение, режим `full` и loopback URL. Этот режим не является способом запуска на произвольном существующем стенде. Основная фаза `full` исключает маркер `isolated_admin`; успешная основная фаза сама по себе не означает выполнение проверок последнего администратора. Текущая реализация содержит три последовательных варианта одной функции (ADM-003); конкурентная защита из FR-01 не проверяется (ADM-004).

Источники: [runner](../scripts/run_last_admin_tests.py), [workflow](../.github/workflows/api-tests.yml), [условия запуска](testing-auth.md#отдельный-запуск-защиты-последнего-admin), [проверки](../tests/users/test_last_admin.py). Применимо к текущей реализации runner и CI.

## Известное расхождение схемы профиля

Ранее в документации было отмечено, что OpenAPI допускает `null` для `email` и `name`, а API отклоняет такие значения. Версия той схемы не установлена; актуальность расхождения не подтверждена. FR-01 и REST-спецификация коммита `0d8396f38c8a7b727648585e33b3d34fe54652ab` явно разрешают `null` только для телефона; на них основаны ожидания матрицы профиля. Это статическая сверка, без нового прогона API и проверки генерируемой OpenAPI.

Источники: [матрица профиля](testing-auth.md#profile-checklist), [существующие проверки](../tests/users/test_profile.py), требования и REST-спецификация по ссылкам в начале матрицы. В PRF-016 отражено ограничение: тест `name=null` проверяет отказ и сохранность профиля, но не поле в `details`.

## Формат матриц покрытия

Согласован компактный формат в существующих тематических документах: ID, проверяемое правило с ожидаемым результатом, варианты, важность, покрытие, реализация автотеста. Последняя колонка подтверждает реализацию, а не успешный прогон. Источники указываются для группы, существенные параметры — в вариантах. Статусы: «покрыто» для явно перечисленных вариантов, «частично» с ограничением, «не покрыто» без реализации. Подробное повторение шагов и assertions не требуется; одна строка не равна одному `assert`. Легенда: [docs/README.md](README.md#check-catalog).

Матрицы разделены по согласованному объёму: [testing-bookings.md](testing-bookings.md) — создание, ограничения, доступность, права, чтение, идемпотентность, изменения номера и конкуренция; [testing-booking-lifecycle.md](testing-booking-lifecycle.md) — платежи, отмена, истечение и завершение. В каждом файле есть оглавление; ссылки на ID ведут к записи. Исходные 126 записей и их ID сохранены при разделении; дальнейшие дополнения не меняют прежние ID. Навигация: [карта матриц](README.md#навигация). Это не утверждение полноты покрытия требований: пробелы и ограничения указаны в строках. ID жизненного цикла и CON-001–005 сохранены при преобразовании; CON-005 остаётся ссылкой на CAN-014. В [testing-auth.md](testing-auth.md) все разделы переведены в матрицы; в [testing-hotels.md](testing-hotels.md) матрицами описаны чтение (HCL) и управление отелями (HTM), создание и чтение номеров (RCR), управление номерами (RMT). Перевод тематических обзорных разделов в матрицы завершён; это не означает полного покрытия требований или реализации отмеченных пробелов. Обратная сверка 89 пунктов FR-01–FR-10 requirements.md коммита `0d8396f38c8a7b727648585e33b3d34fe54652ab` выполнена 2026-11-14: [карта FR и границы API-набора](README.md#requirements-audit). Сводка хранится как FR → матрицы → исключения без привязки каждого подпункта. Общие проверки ошибок вынесены перед матрицами; специфичные поля и ограничения остаются в строках. Это полнота учёта данного текста требований, а не полнота тестов, всех комбинаций или генерируемой OpenAPI. Внутренние SQL-механизмы, Argon2, seed/reset, развёртывание и отсутствие внешних списаний API-набором не подтверждены. В HTM-003 отмечено ограничение каскада: один номер и отсутствие проверки отката при сбое; после невалидных POST в HTM-006/008–010 отсутствие новой записи не доказывается. Для детальных типов RoomInput и границ query-параметров дополнительно указаны схемы тела и объявления Query закреплённой версии API, формирующие машинный контракт; это отдельный источник от текста требований. Источник решения — согласование формата матрицы в чате; требования сверены с закреплённой в документе версией API. Важность не заменяет `smoke`. Проверка BKG-003 ограничивает expires_at временем POST + 30 минут с допуском ±5 с; нужны часы API/БД и runner в пределах допуска, точный момент решения под блокировками не доказывается. Границы 1/10 гостей включены в существующие варианты BKG-004/016 без увеличения числа сценариев. Источники — связанные в матрице тесты и FR-04.

Одинаковые проверки не получают вторую строку с новым ID: раздел прав ссылается на CAN-006–008 для отмены, раздел чтения — на EXP-007 и CMP-001–002 для состояний жизненного цикла. Одна функция может подтверждать несколько разных правил. Источник — согласованный в чате принцип и [матрицы](testing-bookings.md#booking-access-checklist).

В сценариях истечения и завершения работающий worker может выполнить переход раньше проверяемого запроса. EXP-001 читает SQL-статусы сразу после 409, до GET, и проверяет единственные системные переходы и сохранность истории при повторных обращениях. Это исключает вмешательство GET, но не worker: сохранение переходов именно запросом оплаты при 409 отдельно не доказано, покрытие частичное. Для компактности набора отдельный вариант с остановкой worker и дополнительная фаза CI не используются; точную изоляцию транзакции целесообразно проверять в тестах приложения. EXP-011/012 остаются непокрытыми.

Источники: [тест истечения](../tests/bookings/test_booking_expiration.py), [чтение статусов и истории](../db.py), [матрица EXP](testing-booking-lifecycle.md#booking-expiration-checklist). Ожидания — FR-05 закреплённой в матрице версии API.
