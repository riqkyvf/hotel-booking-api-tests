# Функциональные требования

Статус: архитектура согласована; уточнения ниже являются нормативными требованиями реализации. Документ описывает продукт, не содержит QA-тестов, чек-листов или намеренных дефектов.

## Область продукта

REST API бронирования физических номеров отелей. Frontend и реальные платежи отсутствуют. API использует префикс `/api/v1`, JSON, UUID и UTC. Swagger — `/docs`, машинная спецификация — `/openapi.json`.

Приложение запускается `docker compose up --build -d`. Compose запускает PostgreSQL 17, одноразовый init (Alembic, seed), API и worker. Состояние БД сохраняется в Docker volume. Повторный запуск не заменяет данные.

## FR-01. Пользователи и авторизация

- Регистрация принимает email, пароль, имя и необязательный телефон; создаёт активного `user`.
- Email приводится к нижнему регистру и обрезается по краям, уникален, не длиннее 254 символов.
- Пароль содержит 10–128 символов; пробелы пароля значимы. Хранится только Argon2-хеш.
- Имя после удаления крайних пробелов содержит 1–100 символов. Телефон: необязательный `+` и 7–15 цифр; может быть `null`.
- Login принимает JSON и выдаёт JWT HS256 на 60 минут с `sub`, `iat`, `exp`, `iss`, `aud`.
- На каждом авторизованном запросе проверяются токен, существование пользователя и активность; актуальная роль берётся из БД.
- GET/PATCH профиля работают только с текущим пользователем. PATCH требует хотя бы одно поле; `null` допускается только для телефона.
- Публичный API не позволяет назначить себе роль, изменить активность или передать хеш пароля.
- Администратор может просматривать пользователей, менять роль и активность. Последний активный admin должен сохраняться даже при конкурентных изменениях.
- Поля `is_active` и `is_available` принимают JSON boolean, без строковой или числовой подстановки.

## FR-02. Деактивация

- Деактивация не удаляет пользователя и не отменяет его бронирования или платежи.
- Ранее выданный JWT перестаёт давать доступ при следующей проверке авторизации; login также возвращает 401.
- Уже авторизованный запрос может завершиться после деактивации. Граница действия — чтение активности в зависимости авторизации, а не время отправки ответа.
- `pending_payment` продолжает удержание до общего срока, после чего истекает. `confirmed` сохраняется и завершается по дате выезда.
- Администратор может читать приватные данные и отменить бронь по общим условиям, включая полный тестовый возврат. Проводить оплату от имени отключённого пользователя нельзя.
- При реактивации доступ к сохранённым данным восстанавливается. Старый JWT может использоваться, только если ещё не истёк.

## FR-03. Каталог

- Отель: название 1–150, город 1–100, адрес 1–250, описание 0–5000 символов; рейтинг 0–5 с одним десятичным знаком.
- Номер принадлежит одному отелю, имеет уникальный внутри отеля `room_number` (1–20 символов).
- Типы: `single`, `double`, `twin`, `family`, `suite`; вместимость 1–10; цена 0.01–9999999999.99 RUB, максимум два знака после запятой.
- Обязательные поля PUT передаются целиком. Поля идентификаторов, времени и архивности доступны только для чтения.
- Публичные списки и детали не раскрывают архивные объекты. Admin видит архивные детали; списки требуют `include_archived=true`.
- Отключённый, но не архивный номер остаётся видимым. Он недоступен для новых бронирований; уже созданные бронирования разрешено оплачивать.
- Архивирование не удаляет историю. Запрещено при действующих `pending_payment` или `confirmed`; просроченные состояния предварительно актуализируются.
- Архивирование отеля атомарно архивирует его номера. Повторное DELETE возвращает 204. Восстановление из архива через API не предусмотрено.
- Уменьшение вместимости не может нарушить действующие бронирования. Перенос номера между отелями отсутствует.
- Изменение цены влияет только на будущие бронирования.

## FR-04. Бронирования

- Бронь создаётся только для текущего пользователя. Admin также создаёт бронь только для себя.
- Заезд не раньше текущей UTC-даты; выезд позже заезда; длительность 1–14 ночей включительно.
- Гости: целое JSON-число 1–10, не больше вместимости номера. Булевы значения и дробные числа не являются допустимыми целыми.
- Интервал `[check_in, check_out)` допускает соседние брони с совпадением выезда и следующего заезда.
- Отель и номер должны быть неархивными, номер — разрешённым для новых бронирований.
- Цена и итог рассчитываются сервером и фиксируются в записи. Передача клиентской цены в теле запрещена как неизвестное поле.
- Новая бронь имеет статус `pending_payment` и срок `expires_at = decision_time + 30 минут`.
- Блокирующие состояния: `pending_payment`, `confirmed`. Пересечения одного физического номера запрещены в API и PostgreSQL.
- Пользователь читает только свои бронирования. Admin — все, с фильтром `user_id`; пользовательский запрос этого фильтра возвращает 403.
- Для чужих приватных ресурсов используется 404, независимо от их состояния.

## FR-05. Точное истечение

- `decision_time` — результат PostgreSQL `clock_timestamp()`, полученный после ожидания бизнес-блокировок. Не используются время начала транзакции или часы клиента.
- Удержание действительно при `decision_time < expires_at`. При равенстве или превышении (`>=`) бронь уже истекла и не может быть оплачена.
- Если запрос пришёл раньше срока, но получил блокировку позже, применяется позднее время решения.
- Если оплата получила блокировку и прошла проверку строго до срока, она может завершиться после срока: результат остаётся успешным.
- Worker актуализирует состояния примерно каждые 5 секунд. Авторизованные чтения брони/платежа, список бронирований, проверка доступности и бизнес-операции также актуализируют затронутые состояния под блокировками.
- Задержка worker не продлевает возможность оплаты и не мешает новому бронированию после актуализации.
- При истечении бронь становится `expired`, её `pending`-платёж — `cancelled`. Эти изменения сохраняются и при ответе 409 на просроченную оплату.
- Завершение проживания: `confirmed → completed` при `decision_time.date() >= check_out` по UTC.

## FR-06. Идемпотентность

- POST `/bookings` требует ключ из 1–128 символов `[A-Za-z0-9._:-]`.
- Область ключа: `(user_id, create_booking, key)`.
- Нормализованные валидированные поля запроса сериализуются канонически; порядок JSON-полей не влияет на хеш.
- Первый успешный запрос атомарно сохраняет бронь, ключ, хеш и JSON-снимок ответа.
- Повтор с тем же телом возвращает **тот же исходный снимок и 201**, даже если бронь уже отменена, истекла, оплачена или завершена; новая бронь не создаётся, срок не продлевается.
- Поэтому статус в повторном ответе может быть историческим `pending_payment`. Актуальное состояние читается GET `/bookings/{id}`.
- Заголовки: `Idempotency-Replayed: false/true`, `Location` на созданную бронь.
- Тот же ключ с другим валидным телом: 409 `IDEMPOTENCY_KEY_REUSED`, независимо от текущего состояния брони.
- До поиска ключа выполняется обычная валидация схемы и авторизация. Невалидное тело возвращает 422, деактивированный владелец — 401.
- После отмены или истечения для новой брони нужен новый ключ. Неудачная операция не занимает ключ. Ключи успешных операций не истекают до сброса БД.

## FR-07. Тестовые платежи

- Только владелец создаёт и симулирует платежи. Admin может их читать, но не оплачивать чужую бронь.
- Платёж создаётся только для непросроченной `pending_payment`-брони; сумма/валюта копируются из неё.
- Одновременно допускается один `pending`-платёж. Повторное создание до его завершения: 409 `PAYMENT_ALREADY_PENDING`.
- `failed` — конечное состояние операции. После него разрешено создать новую операцию с новым ID, пока бронь ожидает оплаты и не истекла. Срок брони не продлевается; число последовательных неудачных попыток не ограничено.
- Успех переводит платёж в `succeeded`, бронь в `confirmed` в одной транзакции.
- Отказ переводит платёж в `failed`, сохраняет причину; бронь остаётся `pending_payment`.
- Повторная симуляция не выполняет повторное списание или изменение результата. Обе симуляции допустимы только для `pending`.
- Приоритет проверок: доступ → актуализация срока → допустимость брони → состояние платежа. Для `expired`: 409 `BOOKING_EXPIRED`; для иных неплатёжных состояний: 409 `BOOKING_NOT_PAYABLE`; для завершённого платежа при ещё ожидающей оплаты брони: 409 `PAYMENT_STATE_CONFLICT`.
- В частности, повтор успеха после успеха возвращает `BOOKING_NOT_PAYABLE`, повтор отказа после отказа — `PAYMENT_STATE_CONFLICT`.
- Реальные платёжные данные не принимаются, внешних списаний нет.

## FR-08. Отмена

- Допустима владельцу или admin для `pending_payment` и `confirmed` только при UTC-дате строго раньше `check_in`.
- В день заезда отмена уже закрыта, включая бронь, созданную сегодня.
- `pending`-платёж отменяется. `succeeded`-платёж становится `refunded` с полным тестовым возвратом. `failed` сохраняется.
- Бронь становится `cancelled`, перестаёт блокировать номер. Все изменения атомарны.
- Повторная отмена `cancelled` возвращает 200 с актуальным ресурсом, включая после наступления даты заезда; новый возврат не создаётся.
- Для `expired` и `completed` — 409 `BOOKING_STATE_CONFLICT`. Для неотменённой действующей брони в день заезда и позднее — 409 `CANCELLATION_CLOSED`.

## FR-09. Конкуренция

- Изоляция PostgreSQL — READ COMMITTED. Создание брони сериализуется по ключу идемпотентности и физическому номеру.
- Основной порядок: advisory lock ключа (только создание) → shared-lock отеля → exclusive-lock номера → бронирования → платежи.
- Массовые операции используют упорядочивание по hotel_id, room_id; архивирование отеля начинает с exclusive-lock отеля.
- Два пересекающихся бронирования с разными ключами: одна успешная бронь, второй запрос — 409 `ROOM_NOT_AVAILABLE`. При одинаковом ключе и теле: одна бронь, два ответа 201 с одним ID.
- Два создания платежа: один 201, второй 409 `PAYMENT_ALREADY_PENDING`.
- Две симуляции одной операции: первая определяет результат, вторая получает 409 по правилам FR-07.
- Оплата против отмены до заезда: если оплата первая, она возвращает 200, затем отмена возвращает 200 и оформляет возврат; если отмена первая, оплата возвращает 409 `BOOKING_NOT_PAYABLE`.
- Две отмены: обе возвращают 200, возврат выполняется один раз.
- Оплата против истечения: решение определяется сроком после получения блокировки, а не порядком прихода HTTP-запросов.
- Ожидание блокировки ограничено 10 секундами, SQL-запроса — 30 секундами. Тайм-аут/взаимоблокировка/конфликт сериализации: 409 `CONCURRENT_OPERATION`, транзакция откатывается; запрос можно повторить. Для создания брони сохраняется тот же ключ.
- Exclusion constraint и частичные уникальные индексы служат дополнительной защитой БД.

## FR-10. Контракт и эксплуатация

- JSON-модели запросов отклоняют неизвестные поля. Ответы не содержат секретов.
- Списки имеют `items`, `total`, `limit`, `offset`; default limit=20, допустимо 1–100; offset ≥ 0.
- Сортировка: имя поля для возрастания, `-поле` для убывания; дополнительный порядок по UUID. Списки не являются снимком между отдельными HTTP-запросами.
- Ошибки имеют единый envelope; полный перечень основных ограничений и HTTP-кодов находится в `api-specification.md`.
- История состояний хранится в БД и доступна для изучения через DBeaver; отдельные HTTP-эндпоинты истории не добавляются.
- Seed атомарен и повторяем, содержит 5 пользователей, 5 отелей, 25 номеров, 8 бронирований и 7 платежей. Даты относительны дню seed.
- Сброс выполняется отдельной CLI-командой с явным флагом; API и worker перед ним останавливаются. Публичной операции сброса нет.
